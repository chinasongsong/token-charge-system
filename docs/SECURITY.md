# SECURITY.md

## 安全目标

平台需保障用户身份、API Key、支付链路和调用数据安全，满足最小可运营合规要求。

## 基础控制

- **P0**：`common-security` 提供 JWT 与 API Key 轻量工具；签名密钥与供应商密钥仅从环境读取（运行时注入 UTF-8 字符串或使用 KMS 下发的素材），不得在仓库或容器中写死明文。
- **P1**：`user-center-service` 使用 `JWT_SECRET`（UTF-8，长度满足 HS256 要求）签发访问令牌；密码重置验证码当前经 `VerificationMailPort` 落日志，生产需替换为真实邮件/短信通道并缩短有效期与重放窗口。
- API Key 仅存储摘要（`key_hash`/指纹字段），不明文持久化。
- 敏感配置（供应商密钥、支付密钥）必须通过环境变量或密钥管理服务注入；仓库内仅保留 `deploy/env.example` 等模板，禁止提交含真实密钥的 `.env` 或密钥文件。
- 所有对外接口必须有 TraceID，便于审计追踪。
- 登录、支付、提现等高风险操作启用二次校验（验证码/风控挑战）。

## 数据保护

- 用户敏感数据落库前做脱敏或加密处理。
- 日志中禁止输出密钥、完整手机号、完整身份证号、完整支付凭证。
- 审计日志只增不改，保留策略按合规要求配置。

## 供应商调用安全

- 统一超时、重试和熔断策略，避免放大故障。
- 对供应商返回内容进行安全过滤与错误归一。
- 支持按租户或用户级别进行调用频控和封禁。

## 支付与账务安全

- 支付回调使用签名校验 + 幂等键；**同一订单号**回调路径使用 Redis `SET NX` 短锁（无 Redis 时退化为进程内锁），与 billing **`sourceRef` 入账幂等** 叠加防重复。
- **不得**对长时间未支付的 `INIT` 订单自动入账（与「回调丢失」无法区分）；确认渠道已收款后使用 **`POST /internal/payments/orders/retry-credit`**（`X-Internal-Token`）或等价运维流程触发幂等入账。
- 账务流水与调用订单保持可核对关系。
- 日终/定时任务：先做 **平台内** 一致性自检（如 `COMPLETED` 缺流水、异常 `PENDING`）；与三方支付对账在生产接通道后扩展。

## 漏洞响应流程

1. 记录问题并分级（P0-P3）。
2. P0/P1 立即止血并发布公告。
3. 修复后补充测试与复盘文档。
